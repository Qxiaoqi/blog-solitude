# Plain Language Guide

## Common Rewrites

| 原说法 | 更朴素的说法 | 说明 |
| --- | --- | --- |
| 心智模型 | 可以先这样理解 / 先看这个意思 | 除非真的在讲认知科学，否则通常没必要 |
| 切面 | 方面 / 部分 / 环节 | 多数情况下只是换个普通词 |
| 全景 | 整体 / 一览 / 完整流程 | 标题里尤其容易写得太满 |
| 统一抽象 | 统一接口 / 统一接入方式 | 如果文章讲的是接入层，通常用接口更直白 |
| 横切 | 贯穿各层 / 影响多个部分 | 避免 AOP 味太重 |
| 收敛方式 | 做法 / 比较稳妥的办法 | 不要为了显得高级而绕 |
| 承载 | 负责 / 处理 / 用于 | 大多数句子里都可以直接落地 |
| 沉淀 | 写进 / 整理成 / 存下来 | 技术写作里通常不需要这个词 |
| 编排 | 调度 / 串起来 / 流程控制 | 真在讲 orchestration 系统时再保留 |
| 治理 | 管理 / 约束 / 处理 | 只有在既定领域术语里再保留 |
| 能力边界 | 边界 / 范围 | 通常不是“能力”这个词本身重要 |
| 落在 | 变成 / 走到 / 归到 | 很多句子只是口头套话 |
| 语义化 API | 按用途命名的 API | 尤其适合写给普通工程师看 |
| remediation | 修复建议 | 直接说中文就够 |
| 很重要的工程事实 | 可以看到几件事 / 这里有几点 | 少下判断，多直接陈述 |
| 很关键的判断 | 主要在讲 / 这里的处理方式是 | 避免夸大和讲课腔 |
| 最该先抓住的一点 | 可以先这样理解 | 语气更平 |
| 如果只留一句话，我会建议先记住这个 | 简单说，就是 | 少一点居高临下的导语 |
| 最复杂 | 实现跨度最大 / 涉及文件较多 / 处理项最多 | 没必要动不动排第一 |
| 最成熟 | 实现最完整 / 覆盖最全 | 少一点主观评价 |
| 很工程化 | 这是常见做法 / 这样处理更稳 | 不要把普通工程判断写得像颁奖词 |
| 最值得关注 | 这里主要看 / 这一层主要内容 | 少做阅读指挥 |

## Presentation Rules

### Prefer Mermaid First

- 用 Mermaid 讲系统分层
- 用 Mermaid 讲请求路径、状态变化、组件关系
- 用 Mermaid 讲“前后变化”或“触发顺序”
- 如果一段代码只是为了说明流程，优先改成图

### Use Code Sparingly

- 只有在下面几种情况下再贴代码：
  - 某个字段名、配置名、接口形状本身很关键
  - 某段核心代码本身最能说明机制
  - 某段逻辑不看代码就会失真
  - 需要让读者看到真实输入输出格式
- 如果只是想说明“做了什么”，优先写成一句话或一张图
- 避免连续贴大段源码，尤其是把实现直接搬进正文
- 核心代码可以贴，但只保留解释当前问题真正需要的部分
- 如果真实代码太长、分支太多、工程噪音太重，优先改写成伪代码

### Prefer Pseudocode For Complex Logic

- 适合改成伪代码的情况：
  - 初始化和清理逻辑很多
  - 错误处理、日志、缓存、埋点把主线冲散了
  - 读者真正需要的是判断条件和主流程
- 伪代码要保留：
  - 关键输入
  - 关键判断
  - 关键状态变化
  - 关键输出
- 伪代码后面可以补一句：
  - `对应实现主要在 ...`
  - `实际代码还包含重试、日志和边界处理，这里先省略`

### Function Names Are Secondary

- 先解释行为，再补函数名
- 不要把 `buildSessionContext()`、`guardSessionManager()` 这类名字直接当成段落主标题
- 不要让文章变成“按函数名串讲源码”
- 更适合的写法是：
  - `会话历史在真正参与推理前，会先做一轮清洗`
  - 然后再补一句：`对应实现集中在 ...`

### Keep Heading Numbering Consistent

- 一篇文章里统一一种编号体系
- 推荐：
  - `## 1.`
  - `### 1.1`
  - `### 1.2`
- 避免：
  - 前面用 `## 一、`
  - 后面又切成 `## 2.`
- 同级标题的编号深度和样式保持一致
- 标题如果已经编号，就不要有的编号、有的不编号

## Before And After For Presentation

- 直接贴一段函数实现解释流程
  - 先画 Mermaid 流程图，再补 3-5 句文字说明
- 直接贴一大段复杂函数
  - 抽出主流程，改成 10-20 行伪代码，再补文件和函数名
- 小节标题写成 `### buildSessionContext()`
  - 改成 `### 会话上下文是怎么组装的`
- 正文里连续出现很多函数名
  - 改成先讲行为，再在括号或一句补充里给函数名
- 同一篇里混用 `一、二、三` 和 `1. 2. 3.`
  - 统一成一种

## Keep Or Rewrite

### Usually keep

- 明确的技术对象或代码名：`PluginRegistry`、`ChannelPlugin`、`sandbox`、`tool loop`
- 真实架构概念：`队列`、`schema`、`provider`、`session`
- 领域里已经固化的词，如果换掉会变得更不准

### Usually rewrite

- 只是为了显得“概念化”的词
- 一句话里没有具体动作、对象、边界，只有抽象名词堆叠
- 标题和小节名里的大词：`全景`、`范式`、`闭环`、`心智模型`
- 带讲课口气的导语：`最该先抓住`、`先记住这个`、`很关键的判断`
- 带排行和褒奖色彩的评语：`最复杂`、`最成熟`、`很工程化`
- 大段贴源码来解释本来可以画图说明的流程
- 明明只想解释主流程，却把日志、边界处理、异常分支整段贴出来
- 把源码函数名直接当成文章结构

### Borderline cases

- `抽象`：
  - 讲接口层、抽象层、抽象边界时可以保留
  - 只是说“统一抽象”“这个抽象”时，优先改成 `接口`、`这一层`、`这套设计`
- `编排`：
  - 讲 orchestration 系统、编排引擎时可以保留
  - 普通流程描述里优先改成 `调度`、`串起来`
- `治理`：
  - 讲公认术语如 `服务治理` 时可保留
  - 普通说明里优先改成 `管理`、`约束`

## Review Checklist

- 标题能不能更短、更直接
- 这句话有没有具体主语和动作
- 这段话删掉大词以后，技术意思会不会变差
- 如果不会变差，就改成更直白的词
- 如果一整句都像 PPT，不要逐词替换，直接重写
- 这句是不是在教读者“该怎么理解”，而不是直接把技术内容说出来
- 这个流程有没有机会先用 Mermaid 讲清楚
- 这段代码是不是其实可以缩成一句话
- 这段真实代码是不是更适合改成伪代码
- 函数名是不是抢了正文叙述的位置
- 标题编号是不是从头到尾统一
